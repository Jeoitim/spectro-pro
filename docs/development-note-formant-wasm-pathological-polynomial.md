# 特定录音共振峰分析卡在 93%：Wasm 病态多项式排查记录

## 现象

录音文件：

`C:\baidunetdiskdownload\广东省粤语韵律语料\肇庆鼎湖正序\青年女性（21岁，鼎湖区坑口街道）\04阳上.wav`

该文件每次导入都出现同样的问题：宽带语谱、基频和音强可以完成，共振峰分析长期停在 93%。同目录其他录音正常。

93% 不是一个随机进度，而是 15 个共振峰分析分块中完成了 14 个。卡住的分块包含约 720 个分析窗，说明问题发生在某个确定的分块内部，而不是进度显示错误。

## 文件本身没有异常

目标 WAV 的基本信息：

- 单声道 PCM；
- 44.1 kHz；
- 16 bit；
- 595,488 个采样点，约 13.50 秒；
- 样本均为有限值，没有 NaN、Infinity 或明显削波。

因此不能把问题归因于“文件损坏”或“录音太长”。同一目录中还有更长的录音，但不会触发该问题。

## 根因

### 1. 浏览器解码改变了分析采样率

该 WAV 的原始采样率是 44.1 kHz，但当前浏览器的 `AudioContext.decodeAudioData` 将它解码为 48 kHz。共振峰分析随后按照 Praat Burg 方法把信号准备到约 11 kHz 的分析采样率。

这意味着实际进入 LPC 的样本不是 WAV 中的原始采样序列，而是经过浏览器重采样、再经过项目共振峰重采样的序列。重采样本身不是错误，但它会改变每个短时分析窗里的浮点值。

### 2. 短时 LPC 窗生成了数值病态多项式

共振峰分析使用 10 阶 LPC。每个约 50 ms 的高斯窗经过 Burg 递推后得到预测系数，再组成 10 次多项式。目标录音中有一个中间片段的 LPC 系数使多项式的若干根非常接近单位圆，并且彼此接近。

这类多项式的特点是：

- 系数仍然是有限值；
- 输入音频听起来可以完全正常；
- 采样值发生极小变化时，根的位置可能明显变化；
- 用伴随矩阵求根时，矩阵特征值问题会变得高度敏感。

因此“病态”不等于“非法”。它描述的是数值问题的条件数很差。

### 3. 旧 Wasm 求根器没有收敛上限

旧实现把伴随矩阵交给 `nalgebra::Schur::new(...).complex_eigenvalues()`。这是同步执行的迭代式 Schur/QR 求解：

- 没有在项目层设置可靠的最大迭代预算；
- 一旦某个矩阵长期不能收敛，Wasm 调用会一直占用 Worker；
- JavaScript 线程无法中断正在执行的同步 Wasm 调用；
- 因此任务超时只能在外层记录失败，不能及时挽救当前被卡住的 Worker。

这就是“特定录音固定卡在 93%”的直接原因。

## 与 Praat 的对应关系

项目当前共振峰参数与 Praat `Sound: To Formant (burg)...` 的基本约定一致：

- 5 个共振峰；
- 5500 Hz ceiling；
- 分析采样率约为 ceiling 的两倍，即 11000 Hz；
- 10 阶 LPC；
- 25 ms 有效窗，对应实际约 50 ms 的高斯窗；
- 50 Hz 预加重；
- 低于 50 Hz 和高于 ceiling - 50 Hz 的候选会被丢弃。

Praat 文档也明确说明，LPC 是带有假设的近似模型，并不保证所有语音片段都有可靠的共振峰；其 LPC 根求解同样需要对数值不可靠的根进行过滤。Praat 的根求解使用 Laguerre 方法并进行 root polishing，而不是无限运行一个未设上限的通用特征值迭代。

参考：

- [Praat：Sound: To Formant (burg)](https://praat.org/manual/Sound__To_Formant__burg____.html)
- [Praat：LPC: To Formant](https://praat.org/manual/LPC__To_Formant.html)
- [Praat：Sound: To LPC (burg)](https://praat.org/manual/Sound__To_LPC__burg____.html)

## 修复方案

### Wasm 求根改为有界 Aberth–Ehrlich

Wasm 内不再调用无上限的 Schur/QR 特征值求解，而是使用适合低阶多项式的 Aberth–Ehrlich 迭代：

- 最大阶数限制为 32，项目实际共振峰分析通常为 10 阶；
- 最大迭代次数固定为 256；
- 所有系数和根都必须是有限值；
- 根之间过度重合时立即返回失败；
- 迭代结束后进行归一化多项式残差验证；
- 未收敛或残差过大的多项式返回“本帧没有可靠根”，不阻塞 Worker。

这保证了 Wasm 的关键性质：对病态输入也有有限的执行时间。这里的“失败”是分析结果层面的空结果，而不是任务层面的死锁。

### Wasm 路径不因单帧失败回退 JavaScript

当 Wasm 模块已经成功初始化时，共振峰求根始终走 Wasm。某个多项式无法可靠收敛时只影响该分析窗，不会触发整条任务切换到 JavaScript。只有 Wasm 模块整体不可用时，应用才进入兼容模式。

同时，基频和共振峰的 Wasm 状态分开管理，避免共振峰求根异常让基频加速也被关闭。

### Worker 稳定性

另外修复了 Worker 预热与任务发送之间的竞态：

- 每个 Worker 的 Wasm 初始化只执行一次；
- 分析任务等待初始化确认后再发送；
- 同一个 Worker 的消息串行处理；
- 声学任务使用独立的 15 秒外层保险超时；
- 超时后回收并替换异常 Worker。

外层超时是最后一道保险，不承担中断同步 Wasm 的职责；真正解决卡死的是 Wasm 求根器本身的有界迭代。

## 精度评估

评估使用同一批真实录音，并将旧的 JavaScript 伴随矩阵路径与新的 Wasm 路径逐点对比：

- 8 条同一说话人的粤语录音；
- 约 4 万个有效共振峰点；
- 有效结果的最大频率差约 `1.6 × 10^-11 Hz`；
- 有效结果的最大带宽差约 `2.7 × 10^-11 Hz`；
- 旧路径单独有效、新路径缺失：0 点；
- 新路径单独有效、旧路径缺失：0 点；
- 两条路径同时判定不可靠：5,629 点。

差异处于双精度浮点末位量级，远低于语音学解释中常见的 Hz 级误差，也没有观察到候选根排序变化导致的 F1/F2 跳峰。目标 `04阳上.wav` 在浏览器中重新导入后，三类分析均完成，共振峰不再停在 93%。

## 排查经验

以后遇到“只有某一条录音卡住”的分析问题，可以按以下顺序排查：

1. 先确认文件格式、采样率、声道数、位深、时长和样本是否有限；
2. 区分“某个任务没有完成”和“进度统计错误”；
3. 记录分块数量与卡住的分块编号；
4. 检查浏览器解码后的采样率，而不是只看 WAV header；
5. 将问题分解到单个分析窗，分别测试 Burg 系数、根求解和候选过滤；
6. 对任何迭代式数值算法设置最大迭代次数、有限值检查和残差验证；
7. 不要用 JavaScript 侧超时假设可以中断同步 Wasm；只能回收整个 Worker；
8. 稳定性修复后，必须用真实录音比较频率、带宽和缺失帧集合，不能只验证“不再卡住”。

## 后续可选改进

本次修复解决的是无限迭代和 Worker 卡死。若要进一步减少不同浏览器之间的数值差异，可以考虑对 WAV/PCM 做源采样率保留的解码，避免完全依赖 `AudioContext.decodeAudioData` 的隐式重采样。但这属于输入管线改造，需要单独评估对播放、语谱图和编辑功能的影响。
